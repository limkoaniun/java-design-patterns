# 第5章：会修电脑不会修收音机？——依赖倒转原则（Dependency Inversion & Liskov Substitution）

## 核心思想
业余爱好者也能修电脑，是因为每个部件都插在标准接口上；收音机修不了，是因为所有元件都焊在一起。代码应当像电脑：让每一个依赖都终止于抽象（接口或抽象类），绝不终止于具体细节。作者认为这是面向对象设计的标志："程序中所有的依赖关系都是终止于抽象类或者接口，那就是面向对象的设计，反之那就是过程化的设计了。"[ASD]

## 引入的框架
- **依赖倒转原则（Dependency Inversion Principle, DIP）** — 作者的原话表述 [ASD]：
  1. 高层模块不应该依赖低层模块。两个都应该依赖抽象。
  2. 抽象不应该依赖细节。细节应该依赖抽象。
  - 通俗说法："针对接口编程，不要对实现编程。"
  - 何时使用：当高层策略模块（业务逻辑）原本要直接调用低层工具模块（数据库访问、I/O），而你预期低层一侧会被替换时。
  - 做法：引入一个由高层一侧拥有的接口；业务代码和具体的低层实现都依赖这个接口。结构：`高层模块 → «interface» 接口或抽象类 ← 低层模块`。
  - 为什么叫"倒转"：在过程化代码中，复用是自下而上流动的（高层模块调用低层函数库，因此依赖它）。依赖倒转原则把箭头翻转，让低层细节依赖高层模块所定义的抽象。
  - 故事类比：通过电话就能修电脑，是因为内存、CPU 和硬盘都能对着标准插槽互换（强内聚、松耦合）；收音机修不了，是因为电阻和晶体管彼此焊死（耦合过度）。
- **里氏代换原则（Liskov Substitution Principle, LSP）** — 作者的原话表述 [ASD]："子类型必须能够替换掉它们的父类型。" 较长的说法：使用父类的软件实体必须能在不做任何改动的情况下使用它的任何子类，并且无法察觉其中的差别。
  - 何时使用：每当你要判断 B 是否应该继承 A 时。问一句"凡是用到 A 的地方，换成 B 之后行为会不会改变？"
  - 做法：只有当子类遵守父类所有非私有行为时才继承。如果父类承诺了 `飞()`，不会飞的企鹅子类就违背了承诺；父类只应给出所有子类都能满足的内容（例如 `下蛋()`），否则就不要继承。
  - 为什么重要：里氏代换原则使依赖倒转原则变得安全。之所以能依赖抽象，正是因为任何具体子类型都可以接入而无需调用方改动。它同样使开放-封闭原则所说的扩展成为可能："正是由于子类型的可替换性才使得使用父类类型的模块在无须修改的情况下就可以扩展。"

## 关键概念
- **高层模块 / 低层模块**：业务策略代码与机制代码（例如数据库访问函数）——依赖倒转原则所要倒转依赖方向的那一对。
- **抽象 (abstraction)**：双方都依赖的接口或抽象类；它稳定，所以任何一侧的变化都不会波及另一侧。
- **细节 (detail)**：具体实现类；它易变，必须依赖抽象，绝不能被依赖。
- **强内聚、松耦合**：电脑"易插拔"特性在面向对象中的叫法；每个部件自成一体，只通过标准接口相连。
- **可替换性 (substitutability)**：里氏代换原则的属性；子类实例可以在任何地方代替父类实例。
- **接口 (interface)**：CPU 插槽的类比：定义契约，隐藏任意复杂的内部实现，任何符合契约的部件都能装上。

## 心智模型
- 把你的系统想成电脑，而不是收音机：如果一根坏内存条迫使你更换"主板"，说明依赖箭头指反了。
- 用"谁来定义接口？"作为判断依据：如果高层模块规定契约、低层模块去实现，依赖就被正确地倒转了。
- 把继承看作一种承诺：只有当子类能兑现父类公有方法所做的每一项承诺时，它才是合法的（企鹅不是会飞的鸟）。
- 用里氏代换原则推演系统的增长：因为 `Cat`、`Dog`、`Cow` 都能代替 `Animal`，新增一种动物只会改动实例化的那一处。

## 反模式
- **高层业务模块绑定在具体的数据库层上**：在客户想换数据库之前一切正常；成熟的业务逻辑因为焊死在旧的细节上而无法复用。
- **因为生物学上成立就继承**："企鹅是鸟"在分类学上没错，但如果 `鸟` 声明了 `飞()`，`企鹅 extends 鸟` 就违反里氏代换原则，任何调用 `鸟.飞()` 的代码都会出错。
- **收音机式耦合**：每个组件都引用其他所有组件；故障可能出现在任何地方，除了原作者没人能维护（作者举了一家银行为追查一个故障而停掉服务器大半天的例子）。
- **把"使用了抽象类"当成"是面向对象的"**：检验标准不是语言特性，而是所有依赖是否都终止于抽象。

## 代码示例
本章唯一的代码清单是让里氏代换原则变得具体的可替换性演示：

```java
// Client depends on the parent type only.
动物 animal = new 猫();   // later: new 狗(), new 牛(), new 羊()
animal.吃喝();
animal.移动();            // 跑、飞、游…
// Swapping the concrete subclass changes ONLY the instantiation line;
// every other line that talks to `animal` is untouched.
```
- **它展示了什么**：因为每个子类都能在行为不变的情况下代替 `动物`，调用模块对修改封闭、对扩展开放，这正是依赖倒转原则可以放心以抽象为目标的原因。

依赖倒转原则的结构形态（来自本章的图）：

```java
interface IDataAccess { /* contract the business layer needs */ }   // owned by the high-level side
class BusinessModule { private IDataAccess dao; /* uses only the interface */ }
class MySqlAccess implements IDataAccess { /* detail depends on abstraction */ }
```

## 实战示例
1. **朴素版本（过程化复用）**：每个项目都需要数据库访问，所以这些例程被一次性写成低层函数库。新项目直接调用它。高层依赖低层。
2. **哪里出了问题**：下一个客户想要不同的数据库或存储方式。业务逻辑完全一样，却因为绑定在旧的访问函数上而无法复用。类比：如果 CPU、内存和硬盘都依赖某一块特定的主板，一块主板坏了就会让所有部件陪葬。
3. **重构后的设计**：定义一个业务模块所依赖的接口（或抽象类）；让每个具体的存储实现也依赖这个接口。只要接口稳定，任何一侧都可以变化。
4. **为什么有效**：里氏代换原则保证任何实现都能在调用方毫无察觉的情况下代替抽象，所以调用方永远不需要修改。开放-封闭原则随之而来。
5. **用企鹅做检验**：作者用鸟/企鹅的例子说明，可替换性是一个设计决策，而不是分类学事实：如果父类承诺了 `飞()`，企鹅就不可能是它的子类型。

## 关键要点
1. 让所有依赖都终止于抽象；仅凭这一条检验就能区分面向对象设计与过程化设计。
2. 用作者的方式表述依赖倒转原则：高层和低层模块都依赖抽象；抽象绝不依赖细节。
3. 只有当子类能在所有地方代替父类且行为不变时才继承（里氏代换原则）；否则使用合成或重新设计父类。
4. 里氏代换原则是依赖倒转原则和开放-封闭原则共同的成立条件；应当放在一起讲。
5. 宁要一个可以"通过更换部件来修理"的系统，也不要一个紧凑但焊死的系统。
