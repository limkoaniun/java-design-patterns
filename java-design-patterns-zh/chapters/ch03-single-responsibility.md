# 第3章：电子阅读器vs.手机——单一职责原则（E-reader vs. Phone: Single Responsibility Principle）

## 核心思想
一个类应当有且仅有一个引起它变化的原因。电子阅读器之所以比手机读得更好，是因为它只做一件事；而俄罗斯方块的窗体类若同时包含绘图代码和游戏逻辑，就无法移植、测试或复用，因为两个互不相关的变化原因被焊在了一起。真实设计工作的大部分就是“发现职责并把那些职责相互分离”。

## 引入的框架
- **单一职责原则（Single Responsibility Principle, SRP）** — “就一个类而言，应该仅有一个引起它变化的原因。”[ASD]
  - 故事类比：手机是“不纯粹”的：用它阅读时不断被消息、新闻和广告打断；电子墨水阅读器“只针对阅读来设计产品，做到了功能上的纯粹”。
  - 适用时机：作为对每个类的检验，尤其是初学者往往把业务规则和 SQL 全部堆进去的「Form1」/窗体/控制器类。
  - 做法：(1) 问“能够想到多于一个的动机去改变一个类吗？”；如果能，它就承担了多于一个职责 [ASD]；(2) 列出哪些部分稳定、哪些部分易变（游戏规则 vs. 渲染）；(3) 按每个职责一个类进行拆分；(4) 让易变的一方依赖稳定的一方。
- **职责耦合的代价（Cost of coupled responsibilities）** — “如果一个类承担的职责过多，就等于把这些职责耦合在一起，一个职责的变化可能会削弱或者抑制这个类完成其他职责的能力。这种耦合会导致脆弱的设计，当变化发生时，设计会遭受到意想不到的破坏。”[ASD]

## 关键概念
- **职责（Responsibility）**：一个变化的原因；不是「一项功能」，而是「一条变化轴线」。
- **界面表示逻辑（Presentation logic）**：绘制/擦除方块，把按键映射为调用；易变。
- **游戏逻辑（Game logic）**：下落、旋转、碰撞、移动、堆叠、消行；稳定。
- **沉浸/心流（Immersion / flow）**：作者用来比喻单一用途设计所达到的效果。
- **整合 vs 单一（Integration vs. single purpose）**：两者都是有效的产品策略（智能手机 vs. 电子阅读器）；在代码中，倾向于每个类单一用途。

## 心智模型
- **用「这个类可能因为多少个原因而变化？」作为单一职责原则的探针。** 一个是对的；两个就要拆分。
- **把一个类的易变部分和稳定部分看作等待分离的不同类。** 界面常变；规则很少变。
- **把领域建模为数据，而不是像素。** 俄罗斯方块是一个 `int[10][20]` 网格；下落是 `arr[x][y]` → `arr[x][y+1]`；向左移动的碰撞是 `x-1 < 0 || arr[x-1][y] == 1`；满行是 `x = 0..9` 全为 1。一旦逻辑成为数据操作，界面就只是其上的一个渲染器。
- **手机和电子阅读器都是好产品。** 单一职责原则讲的是类，并不是在论证整合永远是错的。

## 反模式
- **上帝窗体类**：业务算法、数据库 SQL 和事件处理器全都放在 `Form1`/`窗体.java` 里；任何需求都要改它；没有任何东西可复用。
- **以事件处理器的方式思考**：“关键在于各种事件代码如何写吧，这里有什么类可言呢？”是面向过程的思维；事件是入口，不是设计。
- **复制后改动式移植**：把俄罗斯方块移植到 3D/网页/桌面时，复制窗体类再修改，因为逻辑和绘制从未分离。
- **为拆分而拆分**：单一职责原则要求的是一个变化原因，而不是类的数量最大化。

## 代码示例
本章没有代码清单，设计是用文字描述的。以下是作者所述分离方式的最小形态：

```java
// 游戏逻辑：stable, UI-free, independently testable
public class TetrisGame {
    private int[][] arraySquare = new int[10][20];   // 1 = block present

    public boolean canMoveLeft(int x, int y) {
        return x - 1 >= 0 && arraySquare[x - 1][y] == 0;
    }
    public boolean isLanded(int x, int y) {
        return y + 1 >= 20 || arraySquare[x][y + 1] == 1;
    }
    public void clearFullRows() {
        for (int y = 0; y < 20; y++) {
            boolean full = true;
            for (int x = 0; x < 10; x++) if (arraySquare[x][y] == 0) { full = false; break; }
            if (full) { /* zero row y, shift rows above down by one */ }
        }
    }
    public int[][] snapshot() { return arraySquare; }
}

// 界面：volatile; only draws the grid and forwards key presses
public class TetrisForm {
    private final TetrisGame game = new TetrisGame();
    void onTimerTick()  { /* erase, ask game to advance, draw game.snapshot() */ }
    void onLeftKey()    { /* if (game.canMoveLeft(x, y)) move */ }
}
```
- **演示内容**：把 `TetrisForm` 换成 3D 或网页渲染器，`TetrisGame` 完全不用改；游戏规则可以在没有任何窗口的情况下做单元测试。

## 实战示例
小菜被问到打算如何构建手机版俄罗斯方块。他的方案是：一个窗体、一个游戏面板控件、一个开始按钮、一个在每次滴答时绘制和擦除四个方块的定时器、处理左/右/下/旋转的按键处理器、一些 GDI+ 绘图，再加上碰撞、堆叠和消行「散落在各个处理器里的某处」。

大鸟的质问：把这些划分成类。小菜做不到：“这里有什么类可言呢？”他面向过程的习惯是“根深蒂固”的。

关键的问题是：如果现在需要一个 3D 版、一个网页版和一个桌面版，你能复用什么？答案是：什么都不能，因为一切都在一个窗体类里。然而下落、旋转、碰撞、移动和堆叠在各个版本之间从不改变。

分离的做法：把棋盘表示为 `int[10][20]`。每条规则都变成数组操作：移动是索引变化，碰撞是邻格检查，落地是 `arr[x][y+1] == 1`，消行是一次行扫描加下移。这就是游戏逻辑类。窗体类只负责渲染该数组，并把按键翻译成调用。界面变化时，只有窗体类需要改；逻辑原样复用。

小菜的坦率反应：“这个听起来容易，真正要做起来还是有难度的哦！”大鸟的回答就是本章的核心观点：发现并分离职责*正是*软件设计中最难的部分 [ASD]。

## 关键要点
1. 一个类，一个变化原因。
2. 用这个问题检验一个类：「我能想到不止一个修改它的动机吗？」如果能，就拆分。
3. 把易变的表示与稳定的规则分开；让表示依赖规则，绝不能反过来。
4. 把领域行为重新表述为对数据的操作；界面变成一个薄薄的渲染器。
5. 职责耦合会让设计变得脆弱：因为某一个原因而做的修改，会破坏这个类服务另一个职责的能力。
6. 找出职责是设计的大部分工作；不要指望它很容易。
