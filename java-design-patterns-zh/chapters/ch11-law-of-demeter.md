# 第11章：无熟人难办事？——迪米特法则（Law of Demeter (Least Knowledge)）

## 核心思想
一个类只应与它必须交谈的类交谈，并且通过尽可能窄的接口。请求要经由中间人（"IT 部主管"）转发，而不是依赖你碰巧认识的某个具体同事。

## 引入的框架
- **迪米特法则（Law of Demeter, LoD），也叫最少知识原则** — “如果两个类不必彼此直接通信，那么这两个类就不应当发生直接的相互作用。如果其中一个类需要调用另一个类的某一个方法的话，可以通过第三者转发这个调用。”[J&DP]
  - 作者首先强调的前提：“在类的结构设计上，每一个类都应当尽量降低成员的访问权限”[J&DP] — 封装私有状态；不向其他类暴露它们不需要的任何东西。
  - 根本思想：“迪米特法则其根本思想，是强调了类之间的松耦合。” 耦合越弱，越容易复用；修改一个弱耦合的类不会引起连锁反应。“信息的隐藏促进了软件的复用。”
  - 故事类比：小菜上班第一天，只认识 IT 部的小张（由人事小杨介绍）；小张被叫走后，没有其他人愿意帮他装电脑，因为"有事只能找认识的人，对方无空就办不了事"。有了 IT 部主管（或者直接「找 IT 部」），任何有空的技术员都会被指派，小菜不需要认识任何人。
  - 何时使用：每当一个类伸手去访问另一个类的协作者，或者调用方必须知道*具体哪个*对象来干活时。
  - 做法：(1) 字段和辅助方法默认设为 `private`；只暴露调用方需要的部分。(2) 在调用方与一组工作者之间插入协调者/抽象（部门、经理、外观）。(3) 让调用方依赖抽象（"IT 部"），而不是依赖某个人（"小张"）。

## 关键概念
- **最少知识（least knowledge）**：一个类尽可能少地了解其他类的结构。
- **第三者转发（forwarding via a third party）**：如果 A 必须调用 B，可以由中间人转发这次调用，使 A 和 B 不直接耦合。
- **降低成员访问权限**：保持状态为 `private`；只公开必须公开的部分，通常通过属性/getter。
- **松耦合（loose coupling）**：该原则的根本目标；耦合弱意味着一个类的变化不会传播到相邻的类。
- **信息隐藏（information hiding）**：促进复用；该原则与封装（Encapsulation）相互强化，而不是相互冲突。
- **IT 部作为抽象**：部门是抽象类/接口；小张和小李是具体类。调用方应当面向抽象。

## 心智模型
- 把对具体协作者的每一个直接依赖都看作「必须亲自认识某个人」；如果那个人忙碌或离职，你就卡住了。
- 当调用方否则需要认识多个可互换的工作者时，使用「部门」（接口、经理、外观）。
- 「不要和陌生人说话」：一个方法只应调用自身、自身字段、参数或它自己创建的对象的方法，而不是调用从这些对象里取出来的对象的方法。
- 如果一个类暴露了内部细节，其他类顺着它层层访问，就形成了耦合链；隐藏内部细节，只提供一个单一操作。

## 反模式
- **靠关系办事（depending on personal acquaintance）**：`小菜 → 小张` 被硬编码。小张不在时，请求就失败了，尽管小李也能做。在代码中：一个类依赖某个具体实现，而抽象的任何实现其实都可以。
- **工作者之间没有协调者**："一个和尚挑水吃，两个和尚抬水吃，三个和尚没水吃" — 有两个或更多可互换的工作者却没有经理/抽象时，调用方必须自己挑一个，结果就是工作被推来推去。
- **成员过度暴露**：公有字段和辅助方法会诱使其他类依赖你的内部实现，从而把你的实现锁死。

## 代码示例
本章以图示为主，没有代码清单；两幅图在这里以草图形式重建。

```java
// Before: caller coupled to a specific worker
class XiaoCai {
    private XiaoZhang zhang;                 // knows a person
    void getPc() { zhang.installPc(); }      // fails if zhang is busy
}

// After: caller talks to the department; the department assigns work
interface ItDepartment { void installPc(Employee who); }

class ItManager implements ItDepartment {    // the third party that forwards the call
    private List<Technician> staff;          // 小张, 小李 ...
    public void installPc(Employee who) {
        staff.stream().filter(Technician::isFree).findFirst()
             .orElse(staff.get(0)).installPc(who);
    }
}

class XiaoCai {
    private ItDepartment it;                 // knows only the abstraction
    void getPc() { it.installPc(this); }
}
```
- **演示内容**：调用方的知识缩减为一个抽象；具体由哪位技术员干活，在抽象背后决定。

## 实战示例
**情境：** 小菜到岗，人事小杨把他介绍给 IT 部的小张。小张接到一个紧急电话后离开了。小菜等了一整天；小李拒绝处理，因为申请单上写的是小张，而小杨忙得没空重新安排。电脑在下班前半小时才装好。

**诊断（大鸟）：** 失败不是运气不好，而是缺了一层。小菜依赖的是一个*具体*的人；公司没有 IT 主管来分配任务，也没有「谁有空谁处理，事后汇报」的规则。

**修复，三个耦合层级：**
1. 同时认识小张和小李 — 可行，但小菜必须维护与每个工作者的关系（依赖每一个具体类）。
2. 只认识 IT 主管 — 一个依赖；经理转发给任何有空的人（迪米特法则定义中的「第三者」）。
3. 只认识"IT 部" — 即抽象；员工可以全部换掉，小菜的请求照样有效（"哪怕里面的人都离职换了新人，我的电脑出问题也还是可以找IT部解决"）。

第 3 层既是依赖倒转原则（DIP，针对接口编程），也是迪米特法则（知道得最少）。本章以小菜意识到这两条原则是互补而非竞争的关系作结。

## 关键要点
1. 每个成员默认设为 `private`；只公开其他类真正需要的部分。
2. 如果 A 不是*必须*与 B 交谈，就不该交谈；通过掌管这层关系的中间人转发。
3. 依赖部门，而不是依赖个人：面向抽象，这样具体协作者才能被更换或替代。
4. 松耦合是目标；迪米特法则是发现耦合过紧之处的实用规则。
5. 迪米特法则与封装是两种尺度上的同一种直觉 — 把状态隐藏在类内部，把协作者隐藏在抽象背后。
