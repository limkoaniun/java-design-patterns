# 第29章：OOTV杯超级模式大赛——模式总结（Pattern Summary）

## 核心思想
全部 23 个 GoF 模式被拟人化为参赛选手，由六大设计原则担任评委；本章真正的内容是评委逼出来的并排对比，以及收尾的论点：每个模式都是在不同层面上应用抽象（类抽象对象，抽象类抽象类，接口抽象行为）。

## 引入的框架
- **GoF 三大类别** — 创建型（5个）、结构型（7个）、行为型（11个，分为两个比赛小组）。完整表格见「参考表」一节。
- **评委团 = 六大原则** — 单一职责原则（SRP）、开放-封闭原则（OCP）、依赖倒转原则（DIP）、里氏代换原则（LSP）、合成/聚合复用原则（CARP）、迪米特法则（LoD），GoF 担任主持。各模式按其对这些原则的贡献程度接受评判；简单工厂模式（Simple Factory）因违反开放-封闭原则（每次扩展都要修改工厂类）在预选赛中被淘汰。
- **作者对面向对象目的的模型**（面向对象的开场发言）— 面向过程的代码为业务流程建模，而流程恰恰是需求中最易变的部分。面向对象为对象建模，对象更稳定、更封闭；你无法预测会变什么，但通常可以预测在哪里变，面向对象让你把这些地方封装起来。模式是被复用的、经过验证的设计，能把你的思考提升到「山顶」[DPE]。
- **创建型的起点** — “通常设计应该是从工厂方法开始，当设计者发现需要更大的灵活性时，设计便会向其他创建型模式演化。”[DP] 抽象工厂模式（Abstract Factory）、原型模式（Prototype）和建造者模式（Builder）更灵活，但也更复杂。
- **模式精通的四个层次**（出自前言，在此作为全书脉络重述）— 不知道模式；到处滥用模式；全都知道却分不清；要么运用自如，要么干脆不用，无剑胜有剑。

## 关键概念
- **创建型模式**：抽象实例化过程，使系统独立于其对象的创建、组合和表示方式 [DP]；配置可以是静态的（编译期）或动态的（运行期）。
- **高内聚 / 松耦合**：内聚是指一个例程内部各部分关联的紧密程度；耦合是指它与其他例程关联的紧密程度；目标是内部完整，对外小、直接、可见、灵活 [DPE]。
- **找出变化并封装之**：桥接模式（Bridge）的格言，封装各个变化维度。
- **信息的隐藏促进了软件的复用**：迪米特法则对外观模式（Facade）的提问；耦合越弱，修改就越不会产生连锁反应。
- **代码重复 = 最糟糕的坏味道**：模板方法模式（Template Method）的回答；细微的重复隐藏在看似不同、实则相同的结构中 [R2P]。
- **架构模式 vs 设计模式**：MVC 没有出现在比赛中，因为它结合了观察者模式（Observer）、组合模式（Composite）和策略模式（Strategy），是架构模式而不是设计模式。
- **抽象**：终场的论点，类 → 抽象类 → 接口，分别是对「对象 → 类 → 行为」的抽象。

## 心智模型
- 把比赛的分组当作决策地图：痛点在 `new` 时用创建型，痛点在类如何组装时用结构型，痛点在职责与控制流如何流转时用行为型。
- 把代理模式（Proxy）、适配器模式（Adapter）和外观模式看作三种「中间人」：代理模式代表一个对象并控制对它的访问；适配器模式复用已有接口，让两个不匹配的接口协同工作；外观模式在整个子系统之上定义一个新的、更简单的接口（粒度更大）。
- 把桥接模式和适配器模式看作处于不同生命周期阶段的同一招：桥接模式在设计阶段把抽象与实现分离；适配器模式在事后调和已经建好的类。外观模式的裁决：两者无高下之分，解决的是不同的问题。
- 把装饰模式（Decorator）看作子类爆炸的解药：不必为每种扩展组合都建一个子类，而是动态、透明地添加职责，不需要时再移除。
- 把策略模式看作合成优于继承的体现：把行为硬编码进 A 的子类 B、C、D，会让算法与 A 混在一起；把它们封装成策略对象，它们就能独立于 A 而变化。
- 把状态模式（State）看作「条件分支何时可以接受？」的答案：只有当逻辑不会变化、不会增长时才可以；由于这种情况很少见，应把依赖状态的代码分散到各个状态子类中，新增状态就是新增类。
- 把命令模式（Command）和职责链模式（Chain of Responsibility）看作「为什么要把发送者与实现者分开」的两种回答：命令模式使请求可以排队、记录日志、撤销、支持事务；职责链模式则通过沿链传递请求，在运行时确定处理者（县 → 市 → 省 → 国家级医院的转诊）。

## 反模式
- **把简单工厂模式当作最终设计**：因每次扩展都要修改工厂而被淘汰。
- **把「我所知道的模式」当作答案**：粉丝们的口号；Hibernate 押注桥接模式，ADO.NET 押注适配器模式，而评委选了外观模式。
- **每种变化都用继承**：桥接模式、装饰模式和策略模式共同回应的反复出现的失败，即类爆炸和僵化的层次结构。
- **混淆相似的模式**：精通的第三层次；评委的提问就是为了把区别问出来。
- **最后回答并借用所有人的例子**：ADO.NET 对工厂方法模式（Factory Method）终场回答的抱怨，提醒我们「赢家」是把其他模式结合起来的那个模式，而不是某一个最佳模式。

### 评委的两两对比

| 问题 | 作者希望读者记住的答案 |
|------|------------------------|
| 代理模式 vs 外观模式 | 代理模式代表单个对象，客户端无法直接访问目标；外观模式代表一个子系统，客户端仍可直接访问其各部分，只是提供了一个简化的公共接口 [R2P] |
| 代理模式 vs 适配器模式 | 两者都是连接器；代理模式凭空造出一个代表，适配器模式则不然，它为特定用途合成已有的类 [DP] |
| 桥接模式 vs 适配器模式 | 桥接模式在设计之初就做好规划，使抽象与实现能独立演化；适配器模式让两个已设计好的类协作，而无需重新设计任何一方；处于不同的生命周期阶段，没有赢家 |
| 外观模式 vs 适配器模式 | 外观模式定义新接口；适配器模式复用旧接口；适配器模式适配对象，外观模式适配子系统（粒度更粗） |
| 桥接模式 vs 装饰模式 | 两者都对抗继承爆炸；桥接模式通过合成解耦多个独立的变化维度；装饰模式动态且可逆地给单个对象添加职责 |
| 命令模式 vs 职责链模式 | 两者都把发送者与实现者分开；命令模式用于调度、排队、记录日志、撤销、支持事务；职责链模式则因为处理者要到运行时才知道 |
| 策略模式 vs 继承 | 把 A 派生出 B、C、D 会把行为硬编码进 A；策略对象独立于 A 而变化，更易切换、理解和扩展 |
| 备忘录模式的封装条款 | 透明地保存状态会让保存者与 A 的内部实现耦合；备忘录模式向其他对象屏蔽 A 的内部信息，保住了封装边界 |
| 访问者模式的「朋友少」 | 增加具体的 Element 很难；在该结构上增加一个操作只需新增一个访问者 |
| 中介者模式与迪米特法则 | 分散行为会产生大量连接；中介者让对象只认识它自己，从而减少连接，这正是最少知识原则 |

## 实战示例
**终场题目。** 一家年轻的软件公司想要一套内部使用的薪资系统，以后可能对外销售。员工的薪酬类型：正式员工（月薪 + 奖金）、销售人员（底薪 + 提成）、高级管理层（年薪 + 分红）、兼职人员（按小时计）。界面必须有菜单、工具栏、状态栏，朴素易用。先用 SQL Server，但一旦产品化，可能要支持 Oracle/MySQL。有大量查询和统计；有复杂图表，时间允许就自己做，否则购买第三方组件。

各位决赛选手的贡献：
1. **外观 Facade**：典型的企业应用，所以分三层（表现层、业务逻辑层、数据访问层）。业务需求清晰，界面需求模糊。在表现层与逻辑层之间插入一个业务外观层，这样任何界面变化（桌面客户端 vs 浏览器）都不会干扰业务和数据设计。
2. **观察者 Observer**：菜单、工具栏、状态栏意味着每次点击都会触发一连串事件；所有事件机制都是观察者模式，一次状态变化通知所有依赖者。把整个表现层做成事件驱动；状态栏是一个随事件更新的控件。
3. **适配器 Adapter**：「有时间就自己做图表，否则购买」是明确给出的变化点。把它封装起来：按依赖倒转原则，业务模块依赖抽象的图表生成接口，而不是依赖某个组件或自己的代码。第三方组件的接口不匹配时，就对它们做适配。
4. **策略 Strategy**：薪酬规则有好几种，但每种只是计算方式不同；存储和显示都一样。把每条薪酬规则封装成可互换的策略，这样新增或修改规则永远不会触及其余的业务逻辑。
5. **工厂方法 Factory Method**：对象创建不可避免；为了遵守开放-封闭原则、依赖倒转原则和里氏代换原则，对象的使用者不应该知道自己用的是哪个具体对象，所以由一个「对象管理器」工厂负责 [DPE]。把 SQL Server 硬编码进去，到 Oracle 出现时就会吃亏；使用抽象工厂加反射（或 ORM）把业务与数据访问解耦。上面的策略和适配器也都通过工厂创建。从工厂方法模式开始；需要更大灵活性时再转向抽象工厂模式、原型模式、建造者模式 [DP]。工厂方法模式并不会减少工作量，但能防止复杂代码在出现新情况时变得更复杂 [DPE]。

未明说的教训：真实的系统不是「一个模式」；它是层层外观、事件驱动的界面、针对易变规则的策略、第三方边界处的适配器，以及凡是创建会把你钉死在具体类上的地方都使用工厂。

## 关键要点
1. 用原则来评判模式：它是否让你对修改封闭、依赖抽象、可替换、松耦合？简单工厂模式恰恰在这项测试上败下阵来。
2. 创建型设计从工厂方法模式开始；只有在需要抽象工厂模式、原型模式或建造者模式的灵活性时才升级。
3. 成对对比着学习模式（代理模式/外观模式/适配器模式，桥接模式/装饰模式，命令模式/职责链模式，状态模式 vs 分支）；正是这些差异让你能做出选择。
4. 合成/聚合复用原则是桥接模式、装饰模式和策略模式对类爆炸的共同答案。
5. 每个模式背后都是同一个想法，即抽象，应用在对象、类或行为层面；封装变化、松耦合和针对接口编程是它的表现形式。
6. 不要追逐冠军模式；薪资系统的终场展示了五个模式跨层协作。
7. MVC 及类似模式都是由设计模式构建而成的架构模式；不要混淆这两个层面。
